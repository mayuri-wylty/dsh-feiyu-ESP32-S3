# ESP32 第五通道 · TTS provider 对比基准（T29）

> 分支：`esp32/d-t29-tts-bench`（基于 `feat/esp32-channel` 的 `4814e19`，本地提交，不 push）。
> 记录日期：2026-11-10。
> 本文只记录基准方法、实测数据与结论；**不包含任何凭据、绝对路径或本机配置**。
> 参考音频一律以 `config().voice.ref_audio_path`（或环境变量 `FEIYU_TTS_REF_AUDIO`）描述。

## 1. 结论摘要

| provider | 首包 P50 | 首包 P90 | 总时长 P50 | 失败率 | 实时率 |
| --- | --- | --- | --- | --- | --- |
| `sovits-sentence` | **2154.4 ms** | 2690.0 ms | **2154.4 ms** | 0/20 | 1.75x |
| `sovits-stream` | **765.4 ms** | 1480.3 ms | 2420.3 ms | 0/20 | 1.43x |

**默认 provider 建议：`sovits-stream`。**

理由（按 ESP32 实时语音的优先级排序）：

1. **首包延迟是用户唯一能感知的等待。** 流式首包 P50 765ms、P90 1480ms，句级 P50 2154ms、P90 2690ms —— 流式把"第一声"提前了约 **1.4 秒（P50）/ 1.2 秒（P90）**。用户按下说话后等 0.8 秒和等 2.2 秒是两种体验。
2. **总时长差距很小，且不影响体感。** 流式总时长 P50 2420ms 比句级 2154ms 多约 266ms（+12%），但这段多出来的时间发生在**播放已经开始之后**，被播放缓冲吸收；句级则必须等整句合成完才能出声。
3. **失败率相同（都是 0/20），采样率一致（都是 32000）。** 没有稳定性代价。
4. **实时率都 > 1**（1.43x / 1.75x），即合成快于播放，长句不会断流。流式实时率略低是因为 `streaming_mode=2` 走的是"中等质量、较慢响应"的分块路径（见 `api_v2.py` 注释），但 1.43x 仍有 43% 余量。

**保留 `sovits-sentence` 的场景**：需要整句韵律最优、或下游必须拿到完整一句再决定是否播放（例如需要先做整句时长/静音裁剪）时。它单块返回、实现更简单，且总时长更短。

## 2. 环境

| 项 | 值 |
| --- | --- |
| GPT-SoVITS | 本机 `api_v2.py`，仓库 HEAD `59c4468`（2026-11-09），模型 `tts_infer.yaml` 默认 `v2` |
| 服务端点 | `config().voice.sovits_url`（默认 `http://127.0.0.1:9880/tts`），`POST /tts` 可用 |
| 参考音频 | `config().voice.ref_audio_path` 指向的 wav：**9.44 s / 16000 Hz / mono**，302126 字节 |
| 参考文本 | 与参考音频同目录同名 `.txt`（34 字），由 `refTextOf()` 自动对齐 |
| 输出采样率 | **32000 Hz**（两个 provider 都按 WAV 头上报，非 24k） |
| 输出格式 | 16bit PCM mono；流式为 44 字节 WAV 头 + 裸 PCM16LE |
| 队列 | 两个 provider 共用进程内 `getTtsQueue()`，**严格串行**（同一时刻最多 1 个 9880 请求） |
| Node | v24.14.1 |
| 语料 | 20 句中文，5~40 字，硬编码在 `test/esp32-tts-bench.mjs` |

> 为什么必须串行：`getTtsQueue()` 是生产路径上的同一把锁。并发跑测到的是排队时间，不是 provider 本身的延迟。

### 4.3 观察

- **流式首包与句长弱相关**：短句 456~560ms，长句 1200~2200ms。首块大小由服务端分块策略决定，长句首块来得更晚，但仍显著早于整句完成。
- **句级首包与句长强相关**：整句合成完才返回，长句（#20）到 3134ms。
- **流式总时长普遍略长于句级**（+12% 均值），符合 `streaming_mode=2` 的"中等质量、较慢响应"路径特征；对播放无影响。
- **采样率全程一致 32000**，无 24k/32k 混用；下游仍需按 `chunk.sampleRate` 重采样到 ESP32 的 24k。
- **无失败、无超时、无 429**：40 次请求全部 200。

## 5. 复现

```powershell
# 1) 确认 9880 在线
curl.exe -s -o NUL -w "%{http_code}`n" http://127.0.0.1:9880/

# 2) 真实基准（参考音频从 config().voice 读；也可用环境变量覆盖）
cd <repo>
node test/esp32-tts-bench.mjs

# 若 config().voice.ref_audio_path 为空，用环境变量显式指定（不写进仓库）：
$env:FEIYU_TTS_REF_AUDIO = "<参考音频绝对路径>"
$env:FEIYU_TTS_PROMPT_TEXT = "<参考音频对应文本>"
node test/esp32-tts-bench.mjs

# 3) 机器可读
node test/esp32-tts-bench.mjs --json

# 4) 无 9880 环境自检（CI/离线）
node test/esp32-tts-bench.mjs --fake

# 5) 429 指数退避自检
node test/esp32-tts-bench.mjs --fake-429
```

脚本行为：

- 默认先探测 9880（`GET /`，3s 超时）；不可达或参考音频缺失时**自动降级为 `--fake`**，退出码 0。
- 429 限流：指数退避 1s/2s/4s/8s/16s，最多 5 次重试，不中止。
- 两个 provider 串行跑完全部 20 句，句间 100ms 间隔。
- 该脚本**不在 `npm test` 里**（依赖真实服务）；`package.json` 的 `test/esp32-*.mjs` glob 会扫到它，因此脚本检测 `NODE_TEST_CONTEXT` 后直接跳过，不影响全量测试。

## 6. 与既有测试的关系

- `test/esp32-tts-test.mjs`（T16 句级）、`test/esp32-tts-stream-test.mjs`（T18 流式）用 fake fetch 覆盖协议/解码/超时/abort/队列语义，不连真实服务。
- 本基准只做**端到端延迟对比**，不重复上述单元测试；它验证的是"真实 9880 + 真实参考音频"下的体感差异。
